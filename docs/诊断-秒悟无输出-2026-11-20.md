## 一、结论（一句话）

**上游一直在出字，产品的翻译层看不到。**

正文藏在 `ui_event.data.data.delta`（比 `sse.js` 的 `textOf` 多一层 `data`），
`ui:agent_message_update` 被当成「快照」处理，取不到正文 → `translateEvent` 返回 `{}` →
整条流一个字都不发，最后由 `ui:agent_finish_reason` 补一个空 `finish stop`，
表现正好是「能发、正常结束、零输出」。

另外实测发现**第二根因**：`ui:agent_finish_reason` 比 `task_complete` **先到**，
而它被列进 `TERMINAL_EVENTS` → `translator.closed` → `provider.stream` 直接 `break`，
于是带着完整终稿的 `task_complete.text` 永远读不到。

## 五、根因裁决（逐条对设计文档嫌疑 1-5）

### 嫌疑 1「事件名漂移 / sse.js 名单硬编码」→ **成立，但漂的不是事件名，是载荷层级 + 语义**

- 事件名没变：`ui:agent_message_update` 仍在 `SNAPSHOT_EVENTS`（`sse.js:33-38`）。
- 漂的是正文位置：实测形状是 `{type:'ui_event', data:{type:'ui:agent_message_update', data:{messageId, delta}}}`，
  `textOf(data)`（`sse.js:49-65`）只在**第一层** `data` 上找 `text/delta/content/…`，
  第一层只有 `type` / `data` 两个键 → 永远 `undefined` → `translateEvent` 返回 `{}`（`sse.js:112-114` 静默丢弃）。
- 语义也错：那个字段叫 `delta`，是**增量**，产品却把它归进 SNAPSHOT 分支。
- 证据帧：§3.2 两条 + 统计表「已知事件但取不到正文 = 8」。

### 嫌疑 2「#diff 非前缀快照整段丢弃」→ **本轮不成立，但修法不对会立刻变成次生 bug**

- 本轮 `#sent` 始终是空串（正文根本没进 translator），`#diff` 一次都没被触发。
- **警告**：如果只把 `data.data.delta` 接进去、却仍留在 SNAPSHOT 分支，
  第 1 条补 `你好`、第 2 条 `，` 不是前缀 → `#diff` 返回 `''` → 输出会退化成只有「你好」。
  这条必须和「改判增量」一起做，见 §6.2。

### 嫌疑 3「`mode:'chat'` + `extraParams.llmMode` 形状猜错，start 200 但任务没跑」→ **不成立**

- start 响应 `data.status = "accepted"`、有 `taskId`、`generationId`、`replayed=false`。
- query 流里 `agent_state.data.status` 从 `idle` 变 `running`，且 `taskId` 与 start 返回的一致。
- 随后正文帧按时到达（首字 +2.9s，末字 +3.1s）。**请求体形状是对的，不要动。**

### 嫌疑 4「`ensureProject` 复用第一个项目 / projectId 形态不对」→ **不成立**

- `projectId = d489xxqshypq`（即 `url_id`），项目详情：
  `{"id":"541309","url_id":"d489xxqshypq","name":"空白项目","type":null,"status":"active","conversation_rounds":10}`。
- 列表 200、详情 200、start 200、流 200 —— 项目形态与 `projectIdOf` 只认 `url_id` 的判断都成立。

### 嫌疑 5「订阅时序（query 先挂收不到帧）」→ **不成立**

- 产品顺序（query -119ms 先挂，start 后发）：19 帧，内容完整。
- 对照「先 start 后 query」：同样收到 32 帧、同内容（`--contrast` 实测）。
- **附带发现**：`/api/agent/query?projectId=X&taskId=Y` 带 `taskId` 参数时，
  `connected` 之后 20s 零帧 —— **query 只认 `projectId`，不要加 `taskId` 订阅参数**。

### 新增嫌疑 6「`ui:agent_finish_reason` 提前终止读流，终稿 `task_complete` 永远读不到」→ **成立**

- 帧序实测：`… ui:agent_finish_reason → ui:agent_token_usage → state_change → ui:agent_task_end → task_complete`。
- `TERMINAL_EVENTS`（`sse.js:21`）含 `ui:agent_finish_reason` → `translator.closed=true`
  → `provider.js:583` `if (translator.closed) break` → `task_complete.text`（完整终稿）被丢弃。
- 影响：本轮靠 delta 也能还原正文，但只要某轮上游只发终稿、或 delta 全被丢，
  「终稿补差集」这条设计就完全失效 → 继续零输出。属必修。

### 结构性缺陷确认

- **D5a 零可观测性（成立）**：8 帧带正文被静默丢弃，产品无任何计数/日志。原始帧 23 → parsed 19，
  差额是 `finish_reason` 之后产品主动不读的 4 帧；`sseEvents` 本身解析成功 23/23，没有解析失败帧。
- **D5c 空流假成功（成立）**：正文 0 字、error 帧 0 个，translator 仍补 `finish stop`（chunk 1 个），
  宿主看到的是「正常结束」。
- **D5b 取消不上游**：本任务未测（需产品侧改造后验），沿用设计文档结论。

## 六、给 T4 的修复指令（照这个改，不要扩面）

风险登记沿用 F5：**名单先按下面改，不要顺手把三张名单改成模糊正则**（实测事件名一个都没漂，模糊匹配只会增加误判面）。

### 6.1 `src/meoo-web/sse.js:49-65` `textOf()` —— 下钻一层

在第一层候选字段全部落空时，再对 `data.data` 跑同一套候选（**顺序必须是「先第一层，取不到再看第二层」**，
因为真正快照事件 `ui:add_agent_message` / `ui:sync_messages_update` 的正文可能仍在第一层）：

```js
// 上游把正文再包一层：{type:'ui_event', data:{type:'ui:agent_message_update', data:{messageId, delta}}}
const nested = data.data
if (nested !== null && typeof nested === 'object') {
  const inner = textOf(nested)   // 复用同一套候选顺序
  if (inner !== undefined) return inner
}
```

注意：`delta: ""` 的空串必须继续返回 `undefined`（现有候选逻辑已具备 `!== ''` 判断，别改掉）。

### 6.2 `src/meoo-web/sse.js:24-30 / 33-38` —— `ui:agent_message_update` 从快照改判增量

实测 `data.data.delta` 是增量片段（`，`、`钱禹舟`、`！` 各自成帧），不是累计快照：

- 从 `SNAPSHOT_EVENTS` 移除 `'ui:agent_message_update'`；
- 加进 `DELTA_EVENTS`。

若担心上游某天又给累计值，**不要**在 `#diff` 里放宽；在 DELTA 分支加一条自愈即可（低风险、可回退）：
「新片段若以已发内容为前缀且更长 → 按快照补差集，否则按增量追加」。

### 6.3 `src/meoo-web/sse.js:21` —— 把 `ui:agent_finish_reason` 从 TERMINAL 拿掉

```js
const TERMINAL_EVENTS = new Set(['ui:agent_task_end'])   // finish_reason 先到，不是流终点
```

`task_complete` 本身已有 `done: true` 分支（`sse.js:84-87`），`ui:agent_task_end` 兜底；
这样 `provider.js:583` 的 `break` 会发生在终稿之后，`task_complete.text` 才能进 `#diff`。

### 6.4 `src/meoo-web/provider.js:585-588` —— 空流不许假成功（D5c）

「全程零正文 + 零 error 帧」时不要补 `task_complete` 收尾，改成
`finish reason = {kind:'error'}` 或直接抛
「上游没有返回任何内容（已记录 N 个未知事件，开 MEOO_DEBUG=1 看帧）」。
判据用 translator 侧计数（见 6.5），不要用「流结束了」当成功。

### 6.5 D5a 诊断常驻（配套，别漏）

- `MeooSseTranslator` 构造收 `{onUnknown}`：`translateEvent` 返回 `{}` 之前把原始 payload 交回去；
- 默认只记计数；`MEOO_DEBUG=1` 时写 `~/.dsh/get-it-for-free/meoo-web-frames.log`（环形 200 条）；
- 建议直接把这四类标成「已知无正文」，不刷 warn：
  `ui:agent_chat_state`、`ui:agent_context_source`、`ui:register_message_id`、`ui:agent_token_usage`。

### 6.6 顺手可做（不在 D5 主线上，别抢批次）

- `ui:agent_token_usage` 在 `finish_reason` 之后到达，现在整条被丢弃；若宿主侧要 usage，
  得先解决 6.3 的提前 break，再在 translator 里认这个事件。
- 「先 query 后 start」的顺序**保持现状**（对照实验证明两种顺序都收得到帧），
  但 `openChat` 的注释（`session.js:757-763`）里「反过来会丢首帧」这句**没有实测支撑**，
  建议降级为「两种顺序实测都可用，保留先挂订阅以压首字延迟」——别让下一轮再按错误理由改代码。

## 八、探针自身的两个坑（记录，避免下一个人重踩）

1. **`sseEvents` 的 `reader.cancel()` 挂在 tee 上**：`for await … break` 会触发生成器 `finally` 里的
   `await reader.cancel()`，而 `response.clone()` 的另一半还在读 → cancel 可能永不 resolve，
   探针整轮卡死（首版就是这样撞上 60s 自杀的）。探针改为「收流加 4s 硬上限，证据已落 stats 就不等」。
   产品侧 `provider.stream` 走同一条路，只是它在一个游离的 async IIFE 里，表现为「手柄泄漏」而非卡住界面。
2. **原始帧计数要把心跳分开**：SSE 心跳是只有 `:` 注释的块，首版把它算进「原始帧」，得出 36 帧 vs parsed 25 帧
   的假差距，误导「有 11 帧被丢弃」。修正后实测主场景 23 原始 / 19 parsed，差额 4 帧全是 `finish_reason`
   之后产品主动不读的帧。
