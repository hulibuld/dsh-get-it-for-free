## 一、缺陷台账（按用户报的问题对号）

### D1【High】底部「添加渠道」与「未接入渠道」两个入口重复
- 位置：client.js:5501-5519（未接入渠道）与 client.js:5522-5539（＋添加渠道）。
- 根因：两套语义各做一个按钮——
  - `emptyProviders` = 未收起且无启用账号的渠道（5350-5351，`hasAccount = statuses[id].accounts.enabled > 0`）；
  - `hiddenProviders` = 被「×」收起的卡（5353-5354，FIXED_CARDS + CHANNEL_PROVIDERS ∩ hidden）。
  两个按钮长得一样（`ofm_btn ofm_addbtn`、都是「＋ xxx (N)」），用户无法区分「没登录」和「被收起」。
- 影响：页面底部两行重复入口；且「未接入」集合随登录状态漂移，同一渠道一会儿在这行一会儿在那行。

### D2【High】点「未接入渠道」展开的是完整大卡，不是缩略 chip
- 位置：client.js:5509-5519 —— `showEmpty` 展开后 `emptyProviders.map(channel => h(ChannelCard, …))`，渲染的是与已接入渠道同规格的完整 ChannelCard（含账号折叠区、模型折叠区、余额条、测试/刷新按钮）。
- 对照：「＋添加渠道」展开用的是 `ofm_addchip` 小徽章（5531-5539），那才是添加操作该有的形态。
- 影响：想接一个新渠道要在十几张大卡里翻，添加动作（点＋登录）淹没在无关按钮里。

### D3【High】秒悟网页版无法添加第二个账号
- 位置：client.js:4400-4429 `startLogin` paste 分支。
- 根因链：
  1. `MEOOWEB_CHANNEL.login === 'paste'`（3447），点「＋」进 paste 分支；
  2. 3.5.3 加的第一级短路：`status.signedIn === true && !status.error` → 直接回执「已接入秒悟。」（4405-4407）——**只要当前账号活着，就永远到不了粘贴框**；
  3. 第二级 `model.refresh` force 只会重抄当前账号的浏览器登录态，不建新账号；
  4. 于是「添加账号」按钮在已登录状态下语义变成「确认已登录」，多账号入口被 3.5.3 的修复顺手堵死。
- 后端本身是好的：`accountCreate`（session.js:192-212）append + 切 active，`/meooweb/accounts/create` 路由已存在，`account.use/update/remove` 全通（进度.md 26+16 项测试过）。**纯前端入口问题。**
- 附带缺陷：
  - D3a `accountCreate` 无去重：同一份 cookie 贴两次会建两条账号（session.js:197-209 直接 append）。
  - D3b `adoptBrowserCookie`（session.js:410-438）调 `browserCookieSnapshot` **不传 `preferSessionId`**，且 `writeStored` 写进「当前账号」——多账号下浏览器自愈会把浏览器里最新那份（可能是 B 号）盖到当前 A 号上，**串号**。豆包侧已经用 `preferSessionId` 配对（chromecookie.js:150），秒悟没抄这个作业。

### D4【High】秒悟网页版查不了余额
- 位置：client.js:3936-3939 —— `credits.balances` 硬编码 `return { accounts: [] }`，注释「网页版不给余额数字」。
- 根因：没对接 meoo.com 的额度接口。`CHANNEL_CREDITS['meoo-web'] = { status: true }`（3412）开了余额能力位，但 RPC 回空表 → 卡片永远显示不出数。
- 未知项：meoo.com 真实额度端点（候选：`/api/v1/user/me` 的 data 里可能带 quota 字段；或独立 subscription/quota 接口）。**需要一次带登录态的实测抓包定位**，不能瞎猜端点写死。

### D5【Critical】秒悟网页版能输入、无任何有效输出
- 链路：provider.js:558-601 `stream` → session.js:765-815 `openChat` → sse.js 翻译 → readStream → finish。
- 嫌疑点（按可能性排序，需实测抓帧裁决）：
  1. **sse.js 事件名单硬编码**（sse.js:21-38）：DELTA/SNAPSHOT/TERMINAL 三张名单是按某一次抓帧写死的；`translateEvent` 对未知 `ui:*` 一律返回 `{}`（sse.js:114）——上游若换了事件名/包了层，整条流静默丢弃，最后补一个空 `task_complete` 收尾 → 表现恰好是「能发、正常结束、一个字没有」。
  2. **`#diff` 非前缀快照整段丢弃**（sse.js:208-220）：上游重写整段（快照与已发内容非前缀关系）时返回 `''`，若首个正文事件就是这种快照且 `#sent` 已被 delta 污染，正文全丢。
  3. **`mode:'chat'` + `extraParams.llmMode`**（session.js:788-790）：注释自证「只给 model 上游回默认模型」——请求形状是逆向猜的，start 可能 200 但任务根本没跑（如 projectId 不对、缺字段）。
  4. **`ensureProject` 复用第一个项目**（session.js:730-754）：`#projectId` 缓存 + 取列表第一个；若该项目属于别的形态（如 agent 项目而非 chat），start 静默无效。
  5. **先挂 query 再 POST start 的时序**（session.js:759-800）：query SSE 是项目级长连接，若上游要求「先 start 拿 taskId、再按 taskId 订阅」，现在订阅的是空频道。
- 结构性缺陷（无论根因是哪个都该修）：
  - D5a **零可观测性**：sseEvents 丢弃解析不了的帧、translateEvent 丢弃未知事件，全程无日志无计数。用户与开发者都看不到「上游到底发了什么」。
  - D5b **取消不上游**：session.js:818-829 写了 `stop()`，但 provider.stream 从未调用——用户取消只 abort 本地 fetch，上游任务继续跑完白烧额度。
  - D5c 空流假成功：一条正文都没发也补 `finish stop`（provider.js:585-588），把「无输出」伪装成「正常结束」。

### D6【Medium】豆包工作接入方式绕弯路
- 现状链路（src/doubao/login.js + chromecookie.js + index.js healAccount）：
  1. 点添加 → spawn 一个**全新临时 profile** 的 Chrome（mkdtemp，什么账号都没登）→ 用户在新窗口里重新扫码/输密码 → CDP 轮询抓 cookie → 关窗删目录；
  2. 用户 Chrome 里明明已经登着豆包，却要在空白浏览器里再登一次；
  3. 之后每次发消息前 `healAccount` 都要解密整个 Chrome cookie 库（security find-generic-password + PBKDF2 + 复制 sqlite + 扫 21 个 profile 目录）对齐 s_v_web_id/sessionid，60s 节流；
  4. 失败文案还引导用户「去浏览器开 www.doubao.com 刷新一次再重发」（adapter.js:346）——手动兜底成了常态。
- 根因：登录流设计时假设「拿不到用户浏览器的登录态」，但 chromecookie.js 已经证明能直接读到（healAccount 天天在用）。**登录与自愈两条路读的是同一个库，却让用户多扫一次码。**
- 附带：login.js 的 `connect` 导出注释说「给 meoo-web 复用」，实际 meoo 走的是 cookie 粘贴/浏览器库直读，从未 import——死接口。
- 与全局准则的冲突：AGENTS.md §5.5 禁止临时 profile 浏览器；豆包登录流正是临时 profile（历史代码，审查阶段只记录，改造方向见 F6）。

### D7【Medium】冗余/低效代码
- D7a client.js `loadCredits`（4266）与 `loadBalances`（4273）双轨并存，11+16 处调用点，多个动作两个都调（4373、4530-4531、4583、4627），90s 轮询只轮 loadBalances——loadCredits 是旧签到状态轨，语义重叠。
- D7b scripts/_*.mjs 探针 106 个（交接文档 §5.5 已点名），污染 git status；其中 _mw-live2.mjs 本身有 bug（读 `snap.header`，实际字段是 `cookieHeader`；`Object.keys(Map)` 恒空）——探针不可信会误导后续排查。
- D7c login.js `connect` 导出 + 「meoo 复用」注释（死代码，见 D6）。
- D7d index.js `readChannelStatuses` 只覆盖 pack 渠道；doubao/qwenwork/meoo-web 三张卡各自 REST 喂计数（client.js:5251/5275/5297），三套 loadXxx 结构 90% 相同——可抽一个工厂，但属重构非急修。

## 二、修复设计（最小改动优先，每条对应缺陷）

### F1+F2 合并底部入口为一条「＋ 添加渠道」（修 D1/D2）
- 删掉「未接入渠道」独立按钮与 showEmpty 状态（client.js:5349、5501-5519）。
- 「＋ 添加渠道」的候选集合改为 `hidden ∪ empty`（去重），仍用 `ofm_addchip` 小徽章渲染；chip 上带状态点：已收起/未接入。
- 点 chip 的行为分两类：
  - 被收起的卡 → 现行为（从 hidden 移除，卡回到主网格）；
  - 未接入的渠道 → 从 hidden 语义外直接触发该渠道的登录（复用 ChannelCard 的 startLogin 逻辑，抽成页级函数 `beginChannelLogin(channel)`），登录成功后卡自然进入 filledProviders。
  - 实现取巧：点未接入 chip = 把该渠道 id 加入一个 `pendingLogin` 状态 → 主网格临时渲染这一张 ChannelCard 并自动展开账号区/触发 startLogin → 完成或取消后移除。避免在 chip 里复刻三级登录逻辑。
- 主网格 filledProviders 逻辑不动；emptyProviders 不再渲染大卡。
- 计数 pill（5477-5478）不变。
- 验证：node --check client.js；浏览器实测底部只剩一个入口，chip 形态，点未接入 chip 出登录而非大卡。

### F3 秒悟多账号入口（修 D3）
- startLogin paste 分支改语义：「＋ 添加账号」**永远允许添加**——
  - 已登录时不再短路回执，而是直接 `setLogin({paste:true,…})` 弹粘贴框（框标题文案区分「添加第二个账号」）；
  - 保留「从浏览器重抄」作为粘贴框里的一个次级按钮（现第二级逻辑挪进去），不挡主路。
  - 即：把 3.5.3 的三级顺序倒过来——粘贴框优先，浏览器自愈降级为框内选项。3.5.3 要解决的「明明登录着还让我贴 Cookie」由**卡片状态行**承担（signedIn 时卡上已显示昵称/模型数），不再靠堵添加入口解决。
- accountCreate 去重（session.js:197 前）：解析出的 cookie 提取 `oneday_sid`（或 token 全文）与现有账号比对，命中则返回 `{ok:false,error:'这份登录态已经是账号「X」了'}`，不建新行。
- adoptBrowserCookie 串号修复（session.js:410-438）：
  - 读当前账号 cookie 里的 `oneday_sid` 作为 `preferSessionId` 传入 browserCookieSnapshot；
  - 浏览器里找不到同 sid 的 profile 时**不覆盖**（return adopted:false, reason:'no-matching-profile'），除非当前账号 source==='browser' 且库里只有一份候选；
  - 多账号且当前号在浏览器无对应登录态 → 维持原样，让报错如实指向「请重贴该账号 Cookie」。
- 验证：scripts/_mw-multi.mjs 补去重/串号两个用例；重启宿主后实测贴第二份 cookie → 2 条 → 「用这个」→ 下一轮走新号（交接文档 §5.3 欠的实测）。

### F4 秒悟余额（修 D4）
- 第一步（探针，只读）：写 scripts/probes/archive/_mw-quota.mjs（T7 归档位置），带当前登录态 GET `/api/v1/user/me` 打印完整 data；再按 meoo.com 网页实际请求（browser_* 桥看 network）定位额度端点（候选 /api/v1/user/quota、/api/v1/subscription、user/me 内嵌字段）。

- 端点实测拿不到数字时：如实回 `{accounts:[{accountId,error:'上游未提供额度接口'}]}`，卡片显示原因而不是假 0。
- 验证：探针脚本输出真实数字；卡片余额徽章出数；断网/过期凭据时显示原因不崩。

### F5 秒悟无输出（修 D5，先诊断后修）
- 诊断优先（不许盲改）：
  1. sse.js 加诊断开关：`MeooSseTranslator` 构造收 `{onUnknown}` 回调；translateEvent 返回 {} 前把原始 payload 交给回调；provider.stream 在 `MEOO_DEBUG=1` 时把未知事件/丢弃帧写 logger.warn + 落 `~/.dsh/get-it-for-free/meoo-web-frames.log`（环形截断 200 条）。
  2. 写 scripts/probes/_mw-chat.mjs：用真实凭据走 ensureProject→openChat 全流程，逐帧打印 type/data.type 与正文命中情况——一次跑完就能裁决嫌疑 1-5 哪个是真根因。
- 按裁决结果修（预案）：
  - 事件名漂移 → 名单改为「模式匹配 + 白名单」：`/text_delta|text_stream/` 增量、`/message|assistant_update/` 快照，未知事件带 text 字段时按快照兜底并记日志；

  - start 形状 → 按抓帧对齐网页真实请求体（mode/extraParams/字段名）；

  - D5a 诊断日志常驻（默认只记计数，MEOO_DEBUG=1 记全文）；
  - D5b provider.stream 的 abort 监听里调 `active.stop()`（尽力而为，8s 超时已有）；

- 验证：_mw-chat.mjs 真实出正文；宿主里发一轮见字；取消一轮上游真停；空流场景报错而非假 stop。

## 追加缺陷 D8（2026-11-20 14:30 用户实测报障）

**现象**：codearts 本轮运行失败，界面只剩一句「感谢您的提问，我无法协助完成这个请求…」。

**证据**：`~/.dsh/get-it-for-free/codearts-error.log` 末条（2026-11-20T06:30:13Z）：
`status:200, phase:"sse-error", error_code:"TM.00001024", model:"GLM-5.2"` —— 华为云内容审核在 SSE 流内拦截（HTTP 200 + 流内错误帧）。同日另有大量 502（已有 isTransientGatewayError 处理，非本缺陷）。

**根因**：`vendor/channel-pack/pack.js` consumeSse 的 error_code 分支（约 34671-34699）对 TM.00001024 无专门分类 → 兜底 `LlmError2(INVALID_REQUEST)`；外层请求循环（约 34267-34352）只处理 Quota/BenefitProbe/GatewayRouting/Queue/参数降级，其余直接 throw → DSH 判死本轮。代码注释自证（约 33622）：「当成 INVALID_REQUEST 会被 DSH 直接判死」。
